## 0. 整体思路

那篇文章讲的是「检索怎么做得更准」，但它的前提是**库里已经有一批切好的向量**。
所以工程落地不能照抄文章顺序，必须先把数据链路立起来：

```
文章讲的是后半段                     我们要先补前半段
─────────────────                ─────────────────
查询重写 → 检索 → 融合 → 重排 → 生成     文档 → 清洗 → 切片 → 向量化 → 入库
          ↑                                                    ↑
      这里需要数据                                        阶段一做这个
```

一句话：**先把「数据怎么进去」做扎实、做可见，再谈「怎么取得准」。**
否则检索效果不好时，你分不清是检索算法的问题，还是切片切烂了。

- **阶段 2 必须在阶段 1 之后** —— 没有向量就没得检索。
- **阶段 3/4/5 必须在阶段 2 之后** —— 它们都是「在基础检索结果上做优化」，

  先把不花钱的（混合检索、重排）做掉，再上要额外调 LLM 的。
- **阶段 7（缓存）最后** —— 它是放大器，不是能力。检索还不准的时候缓存只会把错误答案缓存起来。

## 2. 阶段一详解（本次已实现）

### 2.1 数据流

```
上传文件 / 粘贴文本
      ↓  ①接收校验：大小、类型、非空
      ↓  ②SHA-256：内容指纹，用于秒传去重
      ↓  ③落库 kb_document（PENDING）
      ↓  ④解析：PDF(PDFBox) / DOCX(POI) / TXT·MD(UTF-8 优先，GBK 兜底)
      ↓  ⑤清洗：统一换行、删零宽字符、去控制字符、折叠空行
      ↓  ⑥切片：标题 → 段落 → 句子 → 硬切，带 overlap
      ↓  ⑦落库 kb_chunk（PENDING）+ 生成 chroma_id
      ↓  ⑧建集合：get_or_create，cosine，校验维度=1024
      ↓  ⑨向量化：Qwen，每批 10 条
      ↓  ⑩写 Chroma：每批 20 条 upsert，回写 status=STORED
      ↓  ⑪对账：MySQL 切片数 / STORED 数 / Chroma 总数三方比对
      ↓  ⑫完成：文档 DONE
```

### 2.2 关键设计决策

**为什么切片要分层，而不是按 500 字硬切？**

硬切会把一句话、一段代码、一张表格劈开。切在语义边界上，向量才有意义。
所以顺序是：先按 Markdown 标题切 section（标题会继承到每个切片上，检索时能带出去当上下文），
再按空行切段落，再按 `。！？；` 切句子，只有整句都超长才在逗号、顿号处硬切。

实测你那篇文章（39,980 字）的结果是 89 片，平均 431 字，最长 494、最短 230，**硬切 0 次**。
这说明分层策略生效了 —— 没有一句话被劈断。

**overlap 怎么加的？**

不是简单截取上一片最后 80 个字符，而是优先从标点后开始，读起来不会断在半句话上。
代价是切片长度会略超 size（core = size - overlap，所以总长仍控制在 size 附近）。

**为什么 chroma_id 用 `d{docId}_c{index}` 而不是 UUID？**

因为要能对账。日志里出现 `d1_c37` 时，你立刻知道这是文档 1 的第 37 片，
MySQL 和 Chroma 两边都查得到，不用再做一次映射查询。

**为什么写入用 upsert 而不是 add？**

同一份文档重复入库时，`add` 会因为 id 重复直接 400；`upsert` 是覆盖语义，幂等。

### 2.3 观测体系（右侧黑窗口的底气）

三个层次：

1. **实时层**：`SseEmitter`，任务线程每写一条日志立刻推给页面，不轮询。
2. **持久层**：同一条日志同时写 `kb_ingest_log`（带 seq 序号保证顺序）。
3. **回放层**：页面连接时先从 DB 读出该 taskId 的全部历史再挂长连接。
   所以「页面晚开 10 秒」「刷新页面」「关掉再开」都能看到完整过程，
   甚至可以用 `http://localhost:8080/?task=<taskId>` 直接回放某一次任务。

每条日志带四个要素：**时间戳、级别、步骤、耗时**，外加可展开的 detail。
失败时的 detail 不是堆栈倾倒，而是结构化诊断：

```
【分类】NETWORK — 网络连接失败
【目标】Chroma
【异常】java.net.ConnectException
【HTTP 状态】401 Unauthorized + 响应体原文
【根因链】ConnectException → ResourceAccessException
【抛出位置】...
【业务调用点】com.raglab.ingest.service.ChromaClient.ensureCollection(ChromaClient.java:118)
【可能原因】
  - 目标服务没启动，或者端口映射跟配置不一致
【下一步】
  > docker ps --format "table {{.Names}}\t{{.Ports}}" | grep chroma
  > curl http://127.0.0.1:58019/api/v2/heartbeat
```

## 3. 阶段二详解（已实现）

### 3.1 数据流

```
用户问题
   ↓ ①校验：非空、长度 ≤ 500、Top-K 上限 20
   ↓ ②问题向量化：Qwen text-embedding-v4 → 1024 维（必须和文档同模型）
   ↓ ③Chroma 最近邻：/collections/{id}/query，n_results=Top-K
   ↓ ④距离 → 相似度：similarity = 1 - distance
   ↓ ⑤逐条打印命中：#1 0.6421 (距离 0.3579) · 标题 · #切片号 · 正文摘要
   ↓ ⑥写 kb_retrieve_trace（含 hits_json），支持 ?stage=2&trace=<id> 回放
```

### 3.2 实测结果（库里 1160 条向量：89 片 RAG 文章 + 1071 片油气田规范 PDF）

问「大模型的幻觉问题怎么解决？」

```
#1  0.6421  「为什么这么做有效？」        ← 讲查询重写，沾边但不是答案
#2  0.6074  「使用示例」含"缓解幻觉"       ← 这才是直接答案，却排第二
#3  0.6017  「查询重写的原理」             ← 相关
#4  0.5893  「速度提升 820 倍」            ← 讲 HNSW，答非所问
#5  0.5770  「方案1：只取关键句」          ← 部分相关

问题向量 1024 维 / 范数 1.0 / 前 8 维已存库
总耗时 1567ms（向量化 1239ms + 检索 231ms）
```

三个可直接观察到的现象，正是后面优化的靶子：

| 现象 | 说明什么 | 哪个阶段解决 |
|------|---------|-------------|
| Top1 不是最该用的那条 | 向量只算语义相似，不管「哪条最能回答问题」 | 阶段 4 重排 |
| Top4 明显答非所问却排第四 | 缺少「相关度」的第二道判断 | 阶段 4 重排 |
| 1071 片的 PDF 一条没进 Top5 | 向量确实在按语义筛，不是按数量堆 | —（这是好事） |
| 相似度集中在 0.57~0.64 | 中文语义向量就在这个区间浮动，**绝对值无意义，相对排序才有意义** | 阶段 5 上下文控制 |

### 3.3 关键设计

**为什么问题必须和文档用同一个 embedding 模型？**
两个模型各自有独立的向量空间，A 模型产的向量和 B 模型产的向量之间算距离，数值上是能算，
语义上毫无意义 —— 而且**不会报错**。这是最容易踩的静默错误。

**为什么相似度只用来排序，不用来判断「够不够好」？**
`1 - cosine距离` 的绝对值受模型、文本长度、语言影响很大。同一个模型下，
0.58 可能是相关的，也可能是噪音 —— 只有和本次检索里的其他条比较才有意义。
所以前端用色条给出相对强弱，而不是绝对阈值。

**为什么检索也走 SSE 而不是直接返回 JSON？**
因为学习价值在过程里：问题变成的 1024 维向量长什么样、Chroma 里有多少条、
每条命中的距离是多少。这些如果用一次性 JSON 返回，就只剩结果没有推理了。

## 4. 阶段三详解（已实现）

### 4.1 数据流

```
用户问题
   ├─→ ①向量召回：Qwen 转向量 → Chroma 最近邻 → Top-20（语义相近）
   └─→ ②BM25 召回：分词 → 内存倒排索引 → Top-20（字面匹配）
                    ↓
        ③RRF 融合：score(d) = Σ 1/(k + rank)，k=60
                    ↓
        ④按 RRF 分数重排 → 取 Top-K → 写 kb_hybrid_trace
```

### 4.2 三个实现关键点

**① 分词：数字必须整串保留**

```
"Python 3.10 有什么新特性"
  → python / 3.10 / 有什 / 什么 / 么新 / 新特 / 特性
```

如果 `3.10` 被切成 `3` 和 `10`，BM25 就区分不了 3.10 和 3.11 —— 整个优化就白做了。
代码里用「字母数字含 `._-/` 连续串整体作为一个 token」保证这一点。
中文走 bigram（`大模型的幻觉` → 大模/模型/型的/的幻/幻觉），30 行代码替代词典分词器。

**② 索引只收 `STORED` 的切片**

两路召回靠 `chromaId` 对齐。如果 BM25 索引里混入了没写进向量库的切片，
融合时就会出现「只在一边存在的 id」，排名计算会错位。

**③ RRF 的 k 值**

`k=60` 是原论文推荐值。作用是把头部差距压平：
k=60 时第 1 名贡献 1/61=0.01639，第 2 名 1/62=0.01613，只差 1.6%。
如果不加 k（k=0），第 1 名就是 1.0、第 2 名 0.5， rankings 会被第一名垄断。

### 4.3 实测结果

**案例 A：问「match-case 语法怎么用」—— 两路一致，融合稳定**

```
向量 Top3              BM25 Top3                    RRF 融合
#1 sim=0.4644          #1 bm25=14.71                 #1 双路 向量#1 + BM25#1
#2 sim=0.4368          #2 bm25=11.81                 #2 双路 向量#6 + BM25#2（较向量 ↑4）
#3 sim=0.4162          #3 bm25=10.85                 #3 双路 向量#2 + BM25#9（较向量 ↓1）
```

`match-case` 两路都排第 1，融合后没有悬念。

**案例 B：问「数字化交付的模型深度要求」—— 暴露 RRF 的局限**

```
RRF Top3
#1 向量#4 + BM25#3  「本文件及其所代替文件的历次版本发布情况…」   ← 不相关！
#2 向量#6 + BM25#2  「油气田地面工程数字化交付系统应具备…」
#3 向量#2 + BM25#7  「5.1 架构图 5.1.1 数字化交付系统由采集层…」
```

Top1 在两路里都只排第 3-4 名 —— 它不是因为「被强力召回」上来的，
而是因为「两路都出现了」被 RRF 加了两次分。

**这是 RRF 的固有特性，不是 bug。** 日志里会主动打黄色警告提示这个情况，
并把话题引向阶段四：需要用一个真正的相关性模型（交叉编码器）重新判断。

### 4.4 验收标准（已通过）

| 验收项 | 结果 |
|--------|------|
| 数字整串不被切断 | ✅ 分词输出含 `match-case`、`3.10` |
| 两路都召回时融合排第 1 | ✅ 案例 A |
| 显示每条在两路的原始排名 | ✅ `向量#6 + BM25#2` |
| RRF 计算过程可追溯 | ✅ 每条日志 detail 里有 `1/(60+rank)` 展开 |
| 索引自动跟随入库变化 | ✅ 切片数变化时自动重建（1160 篇 635ms） |
| 异常情况有提示 | ✅ 「Top1 在两路里都不靠前」警告 |

## 5. 阶段四详解（已实现）

### 5.1 数据流

```
用户问题
   ↓ ①混合召回：向量 Top-20 + BM25 Top-20 → RRF → 取 Top-20（粗，宁可多）
   ↓ ②重排打分：gte-rerank-v2 逐条给 (query, doc) 对打相关性分
   ↓ ③按重排分排序，算 rankDelta = 召回排名 - 重排排名
   ↓ ④取 Top-K，并单独列出「被挤出」的候选
   ↓ ⑤写 kb_rerank_trace
```

### 5.2 技术选型

选的是 **DashScope `gte-rerank-v2`**，理由：

| 方案 | 落地成本 | 说明 |
|------|---------|------|
| DashScope gte-rerank-v2 ✅ | 最低 | HTTP 调用，和现有 Qwen 同一套 Key，不额外部署 |
| 本地 bge-reranker | 中 | 免费但要跑 Python 服务或转 ONNX |
| LLM 打分 | 高 | 每对都要一次 LLM 调用，最贵最慢，但零依赖 |

**注意接口协议不同**：rerank 走的是 DashScope 原生路径
`/api/v1/services/rerank/text-rerank/text-rerank`，
不是 embedding 用的那个 OpenAI 兼容 `/compatible-mode/v1`。
请求体结构也不一样（`input.query` + `input.documents`）。

### 5.3 实测结果

**单条打分验证**（问「Python 3.10 有什么新特性」）：

```
"Python 3.10 在 2021 年发布，引入了 match-case 语法"  → 0.5287   ← 对的
"Python 3.11 在 2022 年发布，性能提升 10-60%"         → 0.1857   ← 分得清
"这是一段完全无关的关于烹饪的文字"                      → 0.0059
```

对比向量检索：这两段的余弦相似度是 **0.5374 vs 0.4817**，几乎分不开。
rerank 把差距拉到了 3 倍 —— 这就是交叉编码器的价值。

**完整流程验证**（问「数字化交付的模型深度要求」，阶段三 RRF 失败的案例）：

```
阶段三 RRF               阶段四重排
#1 版本发布历史（无关） → #4  ↓3（rerank 0.2304）
#3 5.1 架构图          → #1  ↑2（rerank 0.3552）
#6 数据资产定义        → #2  ↑4（rerank 0.2747）
#8 交付要求            → #3  ↑5（rerank 0.2364）

被挤出 Top-5：
  召回#2 → 重排#6（rerank 0.2126）
  召回#5 → 重排#9（rerank 0.1970）
```

原来排第一的「本文件及其所代替文件的历次版本发布情况」被压到第 4 ——
它只是字面沾了编号「Q/SY 01015」，并不回答任何问题。

### 5.4 重排的局限（要如实记录）

真正讲「模型深度要求」的那段只排到第 5（rerank 0.2303）。原因：

1. 它在 PDF 里是**表格**（`模型交付 / 采集深度要求 采集内容 Ⅰ Ⅱ ...`），
   阶段一的切片把它切成了碎片，表头和数据分了家
2. rerank 模型对表格、列表类内容的判断，弱于自然语言段落

**这不是 bug，是真实系统的常态。** 重排能显著改善排序，但不保证完美。
这个局限正好引出阶段五：与其纠结整个片段，不如把片段里真正相关的**句子**抽出来。

### 5.5 验收标准（已通过）

| 验收项 | 结果 |
|--------|------|
| 两段式流程跑通 | ✅ 召回 20 → 重排 5，699ms |
| 能看到召回排名与重排排名 | ✅ 每条带「召回#3 → #1 ↑2」 |
| 能区分 3.10 和 3.11 | ✅ 0.5287 vs 0.1857 |
| 不相关结果被压下去 | ✅ 版本发布历史 ↓3 |
| 被挤出的候选可见 | ✅ 单独一块展示 |
| 重排分有参考区间说明 | ✅ 日志里给出 >0.5 / 0.2~0.5 / <0.1 的含义 |

## 6. 阶段五详解（已实现）

### 6.1 数据流

```
用户问题
   ↓ ①召回 + 重排（复用阶段四）→ Top-K 源切片，例如 5 片 2255 字
   ↓ ②拆句：按 。！？；切，代码块/表格行整体保留，<8 字碎片并入下一句
   ↓ ③逐句打分：句子级 embedding + 余弦（或关键词覆盖率）
   ↓ ④选句：按分数取，每片最多贡献 N 句，相似度 ≥0.85 只留一条，总长 ≤ maxChars
   ↓ ⑤按原文顺序重排（文档 → 切片 → 片内序号）
   ↓ ⑥拼成 context，写 kb_context_trace
```

### 6.2 两种策略

| 策略 | 做法 | 实测耗时 | 特点 |
|------|------|---------|------|
| VECTOR | 句子级 embedding + 余弦相似度 | ~2.6s | 准，每句都要调 API |
| KEYWORD | 分词覆盖率 ×0.75 + 密度 ×0.25 | ~1.1s | 免费、毫秒级，分不清同义词 |

### 6.3 实测结果

问「数字化交付的模型深度要求」：

```
输入：5 片源切片，2255 字，81 句
输出：20 句，640 字
保留 28.4%，token 估算 3383 → 960
去重丢弃 2 句
```

**最关键的观察**：

```
分数最高的句子：0.6862  「模型交付 / 采集深度要求」  来自源片#5
```

源片#5 正是阶段四里**排第 5 的那个表格切片**。整片排名低，但里面这一句就是答案。
这证明了阶段五的价值：**不要因为整片排名靠后，就丢掉它里面最有用的那句话。**

### 6.4 一个必须记下来的工程优化

第一版把所有 81 句都做了 embedding：8 批请求、**14.7 秒**。交互上完全不可接受。

改成「先用关键词分粗筛出 30 句，只对候选做 embedding 精排」：

```
14.7 秒 → 2.6 秒（5.7 倍）
质量：最高分还是 0.6862「模型交付 / 采集深度要求」，一字不差
```

这是两段式思路的第二次复现（第一次是阶段四的召回/重排）：
**粗筛负责「不漏」，精排负责「准」**。

代价：如果某句关键词完全不沾边、但对向量模型很相关，粗筛会把它漏掉。
实践上这种情况很少，而 10 秒的等待是真实成本。

### 6.5 两个容易忽略的细节

**① 去重不是可选项**

阶段一的 overlap 会让相邻切片开头重复 80 字左右。不去重的话，
你以为压缩了，其实是把同样的话在上下文里说了两遍 —— 既费 token 又干扰模型。

实现用字符 2-gram Jaccard（阈值 0.85），比向量去重快得多，而且 overlap 造成的
重复本来就是**字面重复**，Jaccard 完全够用。

**② 最后一定要按原文顺序重排**

如果直接把高分句子按分数从高到低拼起来，读出来是这样的：

```
4.2 应结合…需求，确定交付内容。
油气田地面工程数字化交付规范      ← 标题跑到中间了
12.1.6 数据交付平台应…
```

跳来跳去，大模型理解费劲，人也读不通。所以最后一步固定按
`(docId, chunkIndex, orderInChunk)` 排序。

### 6.6 验收标准（已通过）

| 验收项 | 结果 |
|--------|------|
| 输出可直接拼进 Prompt | ✅ 页面一键复制 |
| 压缩率 | ✅ 2255 → 640 字，保留 28.4% |
| 去重生效 | ✅ 去重丢弃 2 句 |
| 按原文顺序 | ✅ 句子按文档物理位置排列 |

### 阶段 6：查询重写（对应文章「三、优化1」）

**目标**：解决「用户说瞎编、文档写幻觉」的用词不匹配。

**要写的类**
```
query/
  QueryRewriter     调 qwen-plus 生成 3 个变体（temperature 0.7）
  RewriteCache      常见查询的改写结果缓存
```

**技术点**
- 改写结果必须是「每行一个」，直接 split 换行解析
- 始终把原查询放在第一个，改写只是补充不是替代
- 多查询并发检索后合并去重（按 chunkId 取最高分）

**验收**：输入口语化问题「大模型会瞎编吗」，日志里能看到 3 个改写变体，且最终召回比不改写多。

---

### 阶段 7：多层缓存（对应文章「三、优化5」）

**目标**：命中缓存直接返回，省 LLM 调用。

**分三层**
1. L1 内存（Caffeine）：精确匹配，TTL 按问题类型区分
2. L2 Redis：持久化 + 多实例共享（文章里的 RedisCache）
3. L3 语义缓存：问题向量相似度 > 0.95 直接复用答案

**关键**：知识库更新时必须主动失效 —— 在 `IngestPipeline` 成功入库后清掉相关缓存。

**验收**：日志里打印「L1 命中 / L2 命中 / L3 语义命中（相似度 0.962）」，并统计命中率。

---

### 阶段 8：生成与评估

**目标**：接 LLM 生成答案，并有一套可量化的评测。

**评测集**：准备 20-30 个「问题 + 标准答案 + 应该命中的 chunkId」，
每次改动后跑一遍，看 Hit Rate@3、MRR、答案准确率。

这是整个项目最容易被跳过、也最能体现工程能力的一步 ——
文章最后那句「检索的目标不是找到所有相关内容，而是找到最能回答问题的那几段内容」，
只有靠评测集才能验证。

## 4. 现在就值得记住的坑

| 坑 | 现象 | 原因 |
|----|------|------|
| Qwen 批量上限 | 400 错误 | text-embedding 系列单次最多 10 条文本 |
| 向量顺序错位 | 切片 A 拿到切片 B 的向量 | Qwen 返回的 `data` 数组不保证按输入顺序，必须按 `index` 回填 |
| 维度不匹配 | Chroma 写入报错 | collection 建好时维度就固定了，换模型必须换 collection 名 |
| 扫描版 PDF | 解析出 0 字符，不报错 | PDF 里是图片不是文字，需要 OCR |
| Chroma v1/v2 路径 | 404 | 1.x 用 `/api/v2/tenants/{t}/databases/{d}/collections`，不是 `/api/v1` |
| SSE 丢日志 | 页面刷新后日志没了 | 必须在订阅时从 DB 回放，不能只靠内存推送 |
